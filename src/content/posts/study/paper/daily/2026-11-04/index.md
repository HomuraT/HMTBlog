一个系统“更好”，往往先取决于比较什么。术语说明写得更完整，可能也引入更多细微误解；预训练损失更低，微调后却可能更容易忘记旧知识；Agent 的部署推理更便宜，也可能以昂贵的策略搜索为前提。今天这五篇工作提供了不同的观察窗口：证据从哪里来，能力怎样测，跨任务经验如何积累，以及最终目标是否与代理指标一致。

## 1. OntoDoc：解释本体术语，也要交代依据

给知识图谱增加说明文字，看起来像一项简单的生成任务。然而一个类的真正含义，通常散落在父类、属性、实例、使用方式和领域惯例里。只把术语名字交给 LLM，很容易得到通顺却没有区分度的定义；只翻译 OWL 公理，又容易写成一段人看不懂的形式化结构说明。

OntoDoc 的选择是先搜证据，再写描述。数据库上下文阶段通过 SPARQL 查看目标 IRI，也就是图中术语的唯一标识，探索相关关系与代表实例。网页阶段补充百科和技术背景，随后把两类上下文整理成带理由的结构化假设，最后生成简洁说明。图内上下文被指定为权威依据，网页背景不能任意改写图里的事实。

这个中间层的工程意义在于，审阅者有机会追问一句描述对应哪条三元组。但它并不自动保证事实正确。例如，多个语言标签可以支持“这个概念有多语言名称”，却不能仅凭这一点证明概念在国际上得到广泛认可。让模型写出理由，只是让推断更容易接受审查，仍需要检查理由能否支撑结论。

论文在 151 个术语上实验，包含 DBpedia 的 30 个、BioBricks-MeSH 的 51 个和农业图谱 SOCKG 的 70 个。对照中的朴素方法只取目标 IRI 的出边三元组，再交给 gpt-4.1-mini 生成。使用 kimi-k2.5 的五分制自动评分中，完整性分别从 3.67、3.37、3.26 升为 3.97、3.71、3.84。这更接近“有没有解释出关键语义”的收益，而不是知识推理正确率的提升。

**值得保留的反例**是 DBpedia：准确性从 4.30 变为 4.20，清晰度从 4.73 变为 4.47。扩展证据与丰富文字之间存在取舍。论文另有 11 位人工评审，但他们只评价 OntoDoc，没有做人类评分下的基线比较。因此人工结果支持输出有一定可读性，不能直接证明它对照基线的增益。对于数据目录或本体维护，合理用法是把它作为带证据的文档草稿工具；它没有学习新的本体公理，也没有解决 OBDA 映射或查询重写。

## 2. Hinted Scaling Laws：把零分附近的能力差异显现出来

预测大模型能力时，常见做法是训练一串小模型，再按规模拟合分数。困难在于，如果所有小模型在难题上都接近零分，曲线几乎没有斜率，外推可能由拟合形式主导，而不是由有效观测支撑。

Hinted Scaling Laws 为同一道题连续增加帮助。截断方式给出参考解答的前一部分，遮词方式留下参考解答中的部分文字，另一种方式在生成分数中混入强教师信号。这样原本全错的小模型，也会随着提示量增加逐渐答对。作者同时拟合模型规模和提示强度，再取零提示切片，预测大模型回答原题的表现。

关键区别是“用提示获得测量”，不是“把提示后的高分当成原题能力”。Delphi 阶梯上，作者用训练算量不超过 10^20 FLOPs 的模型，预测 10^23 FLOPs 模型的 GSM8K 准确率；目标实测为 25.9%，预测误差在 3 个百分点内。普通拟合使用同样的小模型和无提示分数时，低估约 13 个百分点。跨所测模型族与 GSM8K、AIME、HLE，预测绝对误差的中位数从 21 降到 4.3 个百分点。

这里的公平比较应说清楚：新方法额外获得了多个提示强度下的评测结果，并不是在完全相同的信息量上白得预测收益。它需要参考解答及额外测量，教师混合还依赖教师访问和 tokenizer 条件。实验中也只有一组明确的统一配方预训练阶梯，后训练模型族可能同时改变数据、训练方式与其他因素。中位误差下降说明方法有价值，不保证未来任务都落在相同误差范围内。

对评测设计更一般的启发是：当所有模型都答错，先检查测量是否太粗。逐步放宽条件，有时能显现原本被地板效应遮住的能力差异。但这种提示需要可核实的参考过程，尚不能直接搬到长期 Agent 或安全测试中。[实现代码](https://github.com/tatsu-lab/hinted-scaling-laws)可以帮助检查拟合与提示协议。

## 3. CoworkOS：长期工作首先需要连续的任务状态

办公和研发 Agent 的困难，并不全在下一步动作选得是否聪明。用户会直接改文档，训练作业要等很久，任务可能被中断，多个执行单元还可能操作同一个资源。如果这些状态只存在于对话历史里，任务一长就容易失去依据。

CoworkOS 将主 Agent 的策略决定、运行时的协调管理和可委派执行分开。主 Agent 决定做什么并验收，运行时维护委派、通信、反馈与长期作业记录。共享应用层让人和 Agent 通过资源标识及版本访问同一份文档、幻灯片或三维场景；工作区与持久语义记忆则保存文件、关键决定和可恢复的运行状态。

在 12 个基准比较中，各框架使用 GLM-5.3、High thinking、256K 上下文和每次最多 64K 输出。CoworkOS 的 Productivity 平均分为 57.54，对照 DeepSeek Harness 为 56.13。它说明完整配置有竞争力，但差距不大，也没有单独验证某种记忆或协调机制贡献了多少。

更具体的案例是自动后训练：GLM-5.3 负责控制与生成数据，Qwen3.6-35B-A3B 接受训练，八项平均分从 33.19 升到 42.95。中间并非一路上升，R2 平均分下滑后，诊断发现 42 条长轨迹占了 84.2% 的监督 token；后续扩大独立轨迹覆盖并改变训练安排。这让“持续工作”有了可观察的实验内容：保留记录、发现数据分布问题、再调整实验。

不过多个因素每轮同时改变，无法把 9.76 分的增长归因于框架本身。JobBench 最终还从 22.66 降为 20.53，R0 与 R1 也分别从基础模型开始。对开发者而言，最有借鉴价值的是状态与责任边界，不是“通用自我改进已经解决”的结论。论文没有证明总时间、token 或算力消耗下降。[代码](https://github.com/RUC-NLPIR/CoworkOS)与[项目页](https://coworkos-ai.github.io/)提供了实现线索。

## 4. Strategist：把推理流程当成可以积累的程序

CoworkOS 关注任务如何持续，Strategist 则关心一次次设计推理流程的经验能否保留下来。模型权重固定，并不意味着只能使用一种推理方式：先拆题、并行尝试、交叉检查、投票或按难度路由模型，都会改变准确率和成本。

Strategist 把这些结构保存成 Python 蓝图，去掉任务专属提示，留下控制流与可复用组件。面对新任务，元 Agent 检索库里的相关结构和跨领域灵感，每轮提出五个候选，在真实样本上运行，再保存表现及经验。这样失败候选也可能成为后续避免重复尝试的依据。

主实验的执行器是 Qwen3 的 0.6B、1.7B 与 4B 模型，每档都有 thinking 开关。18 种基线各跑六种配置，先按训练分数选择基线，再比较测试集。30 个主基准的平均准确率从 74.0% 到 74.7%，每基准相对加权成本的平均为 0.61。另在十个未见基准只检索不继续搜索，准确率为 81.4%，基线为 77.8%。

这些数字需要与成本定义一起读。主实验把 token 数乘以参数规模比例，不是直接测量能耗或云账单；39% 的下降描述推理阶段，不能当成加上元 Agent 搜索后的总成本下降。数据还拆为训练、验证、隐藏选优与最终测试，隐藏集参与选择最优候选，也不能与最终未使用的测试集混为一谈。

实用启发是先保存可执行结构和测量条件，再谈“经验积累”。如果任务流量足够大、题型接近，前期搜索或许可摊薄；如果只有一次性请求，搜索本身可能就不划算。跨模型迁移的积极结果仍需要在自己的任务分布上检验。

## 5. Muon–AdamW：优化器排名取决于最终用途

预训练损失更低，通常被视为更好的起点。但微调还会改变已有知识。一个模型可能更快学会新任务，也可能同时遗忘更多；只看新任务的单个检查点，很容易掩盖这个取舍。

这篇研究比较“新任务学得怎样”和“预训练知识保留多少”构成的最优边界。作者对 OLMo 风格的 30M–600M 模型，使用 150M–154B DCLM token，完成近 600 次预训练和约 29,000 次微调，覆盖 GSM8K、StackMathQA、Alpaca 和 MusicPile，并扫描微调优化器及学习率。

结果是：在按最低预训练损失选择模型的设置下，随着预训练数据增多，AdamW 可以在微调后的学习—遗忘边界上反超 Muon。StackMathQA 中，30M 模型的反转点约为每参数 320 个 token，600M 模型则为 10。这个指标表示训练数据相对于参数量的规模，不是所有模型通用的固定阈值。

作者用 margin-to-spread ratio 提供解释：正确输出分数比错误分数高多少，要相对于错误分数本身的波动来看。这个比值越有利，受到微调扰动后就越可能保留正确输出。简化线性联想记忆中的一步更新定理，以及更长训练的模拟，为机制提供线索，但并没有直接证明真实 Transformer 中的完整 AdamW 必然优于 Muon。

因此可操作的结论是把优化器放回最终训练链条评估：固定数据预算，扫描合理的微调设置，同时看学习与遗忘。不能从 30M–600M 的结果推到所有大模型，更不能只凭一次最低损失排名决定长期配方。

## 继续阅读时应带着什么问题

对于本体工程，先问生成描述的每个关键事实能否追溯到图中证据。对于能力预测，先问额外的提示测量提供了什么信息。对于 Agent，分清一次推理的收益、策略搜索的代价和长期运行的可靠性。对于优化器，直接把最终用途纳入比较，而不是默认代理指标会一直有效。
